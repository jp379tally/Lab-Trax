**Replit Build Brief**

**Objective**
Fix the desktop/web duplicate-doctor merge flow so a user can choose one target doctor and one or more source doctors, causing the `Merge` button to activate and the merge to complete.

**User-visible problem**
From the Customer Center duplicate-doctor notification, the user opens `Review & merge`, selects a target, but the merge cannot proceed. The `Merge` button remains inactive/blocked.

**Likely root cause**
The merge dialog state is treating both duplicate doctor rows as the target, leaving `sources` empty. In the screenshot, the modal shows `SOURCES (0)` and both candidate rows display `Target ✓`. Since the merge action probably requires `targetDoctorId && sourceDoctorIds.length > 0`, the button correctly stays disabled, but the selection UI is incorrectly preventing any doctor from becoming a source.

This is likely a desktop/web-specific regression in the duplicate notification entry path, not the backend merge operation itself.

* Clicking `Merge` sends a payload with one `targetDoctorId` and one or more distinct `sourceDoctorIds`.
* The merge succeeds and refreshes the Customer Center list/duplicate notification count.

**Debug Analysis**

Primary hypothesis: the modal selection state is broken when launched from the duplicate-doctor notification. The strongest evidence is visible in the screenshot: the modal says `SOURCES (0)`, yet both duplicate rows show `Target ✓`. A valid merge needs at least one source, so the disabled merge button is a downstream symptom of invalid UI state.

Alternate hypotheses worth checking:

* The UI is comparing doctors by normalized name instead of stable ID, so both “Dr. Ray montalvo” and “Dr. Ray Montalvo” are considered the selected target.
* The notification path passes duplicate candidates into the modal with the wrong shape, such as setting every candidate as `target` and none as `source`.
* The mobile fix was applied only to a mobile-specific component, while desktop/web uses a separate modal or wrapper.
* The backend requires source IDs, but the frontend never reaches the mutation because the disabled condition remains true.

Recommended approach: fix the frontend state contract first. Do not weaken merge validation. The screenshot shows the app is correctly refusing a merge with zero sources; the real bug is that the UI cannot produce a valid target/source selection.
