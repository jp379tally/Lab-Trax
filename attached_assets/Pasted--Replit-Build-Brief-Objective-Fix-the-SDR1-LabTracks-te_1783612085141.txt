### Replit Build Brief

**Objective**
Fix the SDR1 LabTracks team invite email regression so new-member invites and resend attempts actually send email, and so admins are told when email delivery fails instead of seeing a silent “Pending invite.”

**User-visible problem**
Ben and Alex appear as pending invites in SDR1, but they never receive the LabTrax invite emails. Resending from LabTrax still does not deliver. Their inboxes are working because direct test emails from John arrive normally.

**Likely root cause**
The invite is being created successfully in the database, but the email send is treated as best-effort and can fail silently. In `artifacts/api-server/src/routes/organizations.ts`, both invite creation and resend:

1. create/update the `organizationInvites` row,
2. call `sendInviteEmail(...)`,
3. log `invite email not sent` if `result.sent === false`,
4. still return success to the UI.

So the UI shows “Pending invite” even if LabTrax never actually sent the email.

There is also a suspicious mail preflight in `artifacts/api-server/src/lib/mail.ts`: `sendMail` checks DNS MX/A records before SMTP. That can create false negatives in hosted runtimes or DNS-restricted environments. The safer behavior is to skip only obviously fake/reserved domains and let SMTP decide deliverability for real addresses.

**Code areas to inspect/change**

* `artifacts/api-server/src/routes/organizations.ts`

  * `POST /:organizationId/invites`
  * `POST /invites/:inviteId/resend`
  * shared invite-email helper should be extracted so create and resend behave identically.
* `artifacts/api-server/src/lib/mail.ts`

  * `sendMail`
  * `hasDeliverableDomain`
  * reserved/test-domain filtering.
* `artifacts/api-server/src/routes/auth.ts`

  * `/api/auth/lab-team` returns `pendingInvites`; consider exposing delivery status/error if stored.
* UI that renders the screenshot’s team panel

  * likely desktop settings/profile team component plus mobile `artifacts/labtrax/app/settings/organizations.tsx` if pending invite state is shared.

**Implementation plan**

1. Add explicit invite email delivery handling.

   * Create a helper like `sendOrganizationInviteEmailOrThrow(...)`.
   * It should send the email and return a clear delivery result.
   * If SMTP is not configured, recipient opted out, DNS check blocks it, or SMTP send fails, the route must not pretend the resend succeeded.

2. Store or return invite email delivery status.

   * Best fix: add fields to `organizationInvites`, such as `emailLastAttemptAt`, `emailLastStatus`, `emailLastError`, and optionally `emailProviderMessageId`.
   * If avoiding a migration, at minimum return `{ emailSent: false, reason }` and use a non-2xx response on create/resend failure.

3. Change create/resend behavior.

   * Creating an invite may still create the pending row, but the API response must tell the UI the email failed.
   * Resend should return success only when `sendInviteEmail` returns `sent: true`.
   * If email fails, return a clear `502` or `424` style error: “Invite saved, but email could not be sent. Reason: SMTP not configured / send failed / recipient opted out / domain check failed.”

4. Harden `sendMail`.

   * Keep the reserved/test-domain guard.
   * Do not block real recipient domains solely because DNS preflight fails.
   * Prefer: if MX lookup fails due to runtime/DNS error, log a warning and proceed to SMTP.
   * SMTP is the real authority for whether a recipient can be accepted.

5. Add tests.

   * Test invite create when `sendInviteEmail` succeeds.
   * Test invite create/resend when `sendInviteEmail` returns `{ sent: false, reason: "smtp_not_configured" }`.
   * Test that the API does not return normal success on failed invite email delivery.
   * Test that reserved domains are skipped in non-production/test contexts without causing real sends.
   * Add a regression test for the DNS preflight not blocking real domains when MX lookup errors.

**Guardrails**

* Do not remove invite token security or accept-invite expiration behavior.
* Do not expose raw SMTP credentials or full provider error payloads to users.
* Keep PHI out of logs and emails.
* Do not break existing working invites for George, Lauren, or current team members.
* Preserve account/signup/invitation regression tests listed in `REGRESSION_GUARDRAILS.md`.

**Acceptance criteria**

* Inviting `ben@sdrdl.com` and `alex@sdrdl.com` either sends a real LabTrax invite email or shows an immediate visible failure.
* Resend only shows success when the email was actually accepted by the mail send path.
* The admin can see that a pending invite exists but the last email attempt failed, if it failed.
* Server logs include invite id, recipient domain, and safe failure reason.
* `pnpm --filter @workspace/api-server run test` passes.

**Regression risks to check**

* Existing invite acceptance links still work.
* Pending invite rows still render correctly.
* Invite expiration, cancel, decline, and accept flows still work.
* Email verification/password/security emails are not accidentally blocked or spammed.
* Test fixtures using `example.com`, `.test`, `.local`, etc. still do not send real mail.

### Debug Analysis

**Probable root cause**
The invite workflow is creating valid pending invite records, but email sending is non-authoritative. The backend logs failed delivery and still responds as if the invite/resend succeeded. That exactly matches the screenshot: Ben and Alex exist as pending invite rows, but no email arrives.

**Supporting evidence**
The screenshot shows `ben@sdrdl.com` and `alex@sdrdl.com` as `Pending invite`, so the database invite creation path worked. In `organizations.ts`, create/resend catches email failures and only logs them. In `mail.ts`, `sendMail` can return failure reasons like `smtp_not_configured`, `reserved_domain`, `undeliverable_domain`, or SMTP errors without throwing to the caller.

**Alternate hypotheses worth checking**

* SMTP provider suppression/bounce list has these two recipients blocked.
* Their emails already exist as LabTrax users with `orgInviteNotifications` disabled.
* The invite emails are sent but routed to spam/quarantine.
* `SMTP_FROM`/domain authentication changed and SDRDL’s mail server rejects the sender.

**Why this fix is best**
The core product bug is not only “email failed”; it is “LabTrax says the invite/resend happened even when it did not.” Making delivery status explicit fixes the current issue and prevents future silent regressions.

**Confidence level**
High that silent email failure handling is a real bug. Medium on the exact underlying delivery failure until Replit checks production logs for `invite email not sent` and the `reason` for these invite ids.
