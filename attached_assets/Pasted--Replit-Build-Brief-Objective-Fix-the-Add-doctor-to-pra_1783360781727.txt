### Debug Analysis

**Primary hypothesis**
The success message is coming from the account/membership creation path, but the persistent roster shown in the practice and Accounts page is built from active members plus case-history doctor rows. Dr. Craig’s case-history rows are still attached to the old provider organization, so Craig Dental Associates reloads with only Blake Garfinkel.

**Supporting evidence**

* Screenshot shows Dr. Craig listed as “From case history — will create account.”
* `AddDoctorToPracticeDialog` virtual path calls `POST /organizations/:orgId/doctors`, which creates a provider user and membership but does not move existing case rows.
* `AccountsPage` builds `doctorRows` from `cases`, grouped by `providerOrganizationId`.
* `PracticeDoctorsSection` merges registered members, case history, and pricing overrides. If members are not readable by the lab admin, the new account path will also be invisible.
* `organizations.ts` already has `moveDoctorCasesAndInvoices` for remove/reassign, but the add/link flow does not use it.

**Alternate hypotheses worth checking**

* `GET /organizations/:organizationId/members` is returning 403 for lab admins because it uses direct `requireMembership` instead of parent-lab read access.
* The new membership is created but filtered out because it is inactive, soft-deleted, or the client does not filter status correctly.
* Dr. Craig exists under a slightly different spelling, causing exact name matching to miss cases.

**Confidence level**
Medium-high. The screenshots and code path line up strongly. The one thing Replit should verify in live/dev data is whether the new membership row is actually created and whether the members endpoint is returning it to the current lab admin.
