### Replit Build Brief

**Objective**
Fix the LabTracks “Email statement” workflow so users can successfully send a statement PDF by email, or receive a precise configuration/error message when sending fails.

**User-visible problem**
In the Statement drawer, the user opens **Email statement**, enters `JP@Phillipsdl.com`, and clicks **Send email**. The modal fails with:

`Failed to send the email. Check SMTP settings and try again.`

The PDF appears ready to attach: “The current statement PDF (35 invoices) will be attached.”

**Likely root cause**
The failure is most likely happening server-side during the SMTP send step, not in the statement UI itself. The generic error points to one of these:

* Missing or invalid SMTP environment variables in Replit.
* SMTP auth failure, especially if Gmail/Workspace/Microsoft credentials require app passwords or OAuth-compatible settings.
* Incorrect `from` address or sender verification mismatch.
* Backend email route swallowing the real SMTP error and returning a generic failure.
* Possible recipient casing is not likely the issue; email addresses are case-insensitive in practice.

**Exact areas to inspect/change**

Inspect the backend route or service that handles statement email sending, likely named something like:

* `sendStatementEmail`
* `emailStatement`
* `statementEmail`
* `/api/statements/:id/email`
* `/api/practices/:id/statements/email`
* `mailer`, `smtp`, `nodemailer`, `emailService`, or similar

Also inspect:

* Replit Secrets / environment variables for SMTP config.
* Statement PDF generation path used before attaching.
* Practice billing email fallback logic.
* Server logs around the failed send request.

**Implementation Plan**

1. Locate the statement email API handler and the shared email/SMPP mailer utility.
2. Verify required SMTP env vars are present and read correctly:

   * SMTP host
   * SMTP port
   * SMTP username
   * SMTP password/app password
   * secure/TLS setting
   * from address
3. Add server-side validation at startup or before send so missing config returns a clear admin-facing error.
4. Improve error logging server-side to capture SMTP response codes without exposing secrets.
5. Return safer, more specific client messages:

   * missing config
   * authentication failed
   * connection/TLS failed
   * recipient rejected
   * attachment/PDF generation failed
6. Keep the modal UX the same, but display a clearer message when the backend knows the category.
7. Add a test or manual verification path using a known recipient and a small statement PDF.

**Constraints / Guardrails**

* Do not expose SMTP username, password, tokens, or full provider error details to the browser.
* Do not change invoice balances or statement generation logic unless the PDF attachment is proven to be failing.
* Do not hardcode SMTP credentials.
* Do not silently fall back to sending without the PDF.
* Preserve the practice billing email fallback behavior unless it is broken.

**Acceptance Criteria**

* Sending a statement email succeeds with valid SMTP settings.
* If SMTP settings are missing, the UI says something like:
  `Email is not configured. Add SMTP settings in server environment variables.`
* If auth fails, the UI says something like:
  `Email provider rejected the login. Check SMTP username/password or app password.`
* Server logs include the SMTP failure category and provider response code, but no secrets.
* The statement PDF remains attached to the email.
* Manual test confirms the email is delivered to the requested recipient.

**Regression Risks To Check**

* PDF download still works.
* Text statement still works.
* CSV and PDF export buttons still work.
* Emailing a practice with no billing email still allows manual recipient override.
* Multiple-invoice statements still attach correctly.
* Error messages do not leak credentials or internal stack traces.

### Debug Analysis

**Probable root cause**
The screenshot strongly suggests the UI reaches the send step successfully, but the backend fails while sending through SMTP. The modal has recipient, subject, body, and attachment info populated, so the visible failure is downstream of modal state and likely inside the server email service.

**Supporting evidence**

* The exact error says: `Check SMTP settings`.
* The modal says the statement PDF is already selected for attachment.
* The app UI remains functional; this is not a frontend crash.
* The failure happens only after clicking **Send email**, which usually calls a backend route.

**Alternate hypotheses worth checking**

* The PDF attachment generation fails during send, despite the modal preview text.
* The backend rejects the recipient due to validation rules or provider restrictions.
* The configured sender address is not verified with the email provider.
* The practice email fallback logic is passing an empty or malformed value when the override field is blank. In this screenshot, though, a recipient is present.

**Why this fix is best**
Fixing the SMTP validation and error handling addresses the actual failure path and prevents future support confusion. A frontend-only change would just reword the same dead end. A broad rewrite of email sending would be risky unless the current mailer is structurally broken.

**Confidence level**
Moderate-high from the screenshot. The only missing proof is the backend log or email route code showing the actual SMTP exception.
