### Replit Build Brief

**Objective**
Fix Maynard’s voice conversation mode so clicking the in-app microphone starts live audio capture on the website version, opens the browser microphone indicator, and sends captured speech into the Maynard conversation flow.

**User-visible problem**
Voice dictation works: the browser/OS microphone indicator turns on and speech is transcribed into text. But Maynard conversation mode does not work on PC/web: clicking or activating the conversation microphone does not turn on the microphone indicator, so the app is likely not starting browser audio capture at all.

**Likely root cause**
The dictation feature and Maynard conversation feature are probably using separate microphone paths. Dictation may be using browser speech recognition or a working transcription input, while the Maynard conversation button likely fails before `navigator.mediaDevices.getUserMedia({ audio: true })` is called, or its click handler is blocked by state, permissions gating, feature detection, device checks, or an unsupported voice-session initialization path.

Most likely: the Maynard conversation mic UI is not bound to the same working audio-permission/capture flow as dictation, or it silently fails during voice-session setup before requesting microphone permission.

**Exact app areas to inspect/change**

Inspect voice-related frontend code, especially files/components with names like:

* `Maynard`
* `VoiceConversation`
* `VoiceChat`
* `MicButton`
* `AudioRecorder`
* `useMicrophone`
* `useVoice`
* `useSpeechRecognition`
* `dictation`
* `transcription`
* `conversation`
* API/client code for Maynard realtime or voice sessions

Also inspect any browser permission, feature flag, auth, or environment gating around Maynard voice conversation.

**Implementation plan**

1. Trace the dictation microphone path and identify the exact working microphone acquisition code.
2. Trace the Maynard conversation microphone button path and confirm whether it calls `getUserMedia`.
3. Refactor both flows to use one shared microphone acquisition helper/hook if possible.
4. Ensure the Maynard conversation mic click is a direct user gesture that calls microphone permission/capture immediately.
5. Add visible error states for blocked permissions, unsupported browser APIs, missing voice session config, or failed realtime/audio session startup.
6. Do not show the conversation mic as active unless an actual `MediaStream` is open.
7. Stop tracks cleanly when conversation ends.
8. Add logging around mic permission request, stream start, session connection, audio send, and cleanup.

**Constraints and guardrails**

* Do not confuse browser dictation with Maynard conversation. Treat them as separate flows until proven otherwise.
* Do not only change the icon state. The browser mic indicator must turn on when conversation listening starts.
* Avoid broad rewrites of Maynard chat. Keep the fix scoped to microphone acquisition, voice session startup, and error handling.
* Preserve working dictation behavior.
* If Maynard conversation depends on a realtime API key/session token, fail visibly when that setup is unavailable.

**Acceptance criteria**

* On desktop web, clicking Maynard’s conversation microphone triggers the browser mic permission flow or turns on the browser mic indicator if already allowed.
* Conversation mode receives speech input and sends it into Maynard’s conversational flow.
* Dictation still works exactly as before.
* If microphone access is blocked, unavailable, or the voice session cannot start, the user sees a clear message.
* The mic icon accurately reflects real capture state.
* Ending conversation turns off the browser mic indicator.

**Regression checks**

* No microphone device available.

### Debug Analysis

The strongest clue is that dictation turns on the microphone indicator, but Maynard conversation does not. That means the browser is not receiving a live audio capture request from the Maynard conversation flow, or that request is failing before capture begins.

This is probably not a hardware or browser-level microphone problem, because dictation works on the same PC and same website context. It is more likely an app-level issue in the Maynard conversation path.

Alternate hypotheses worth checking:

* Maynard voice conversation is behind a feature flag or environment variable that is disabled on web.
* The conversation mic button is visually enabled but its handler exits early because Maynard session state is not ready.
* The app initializes a realtime/voice session first, that setup fails silently, and microphone capture never starts.
* The conversation feature uses a different browser API than dictation, and that API is unsupported or blocked on the user’s desktop browser.
* The mic icon state is disconnected from actual `MediaStream` state.

The recommended fix is to unify or closely align the conversation mic acquisition path with the known-working dictation path, then add explicit state and error handling around the Maynard voice-session startup. That targets the real failure point instead of just changing UI state.

Confidence: medium-high based on symptoms. The exact file/function names need repository inspection, but the failure boundary is fairly clear: Maynard conversation is not successfully initiating browser microphone capture.
