### Replit Build Brief

**Objective**
Clean up LabTrax signup so a new lab employee can create a personal account, search for their existing lab, confirm the lab by name/address, and send a join request. Only true lab creators should enter lab setup details.

**User-visible problem**
The current flow asks “Dental lab or dental provider?” and if the user selects dental lab, it assumes they are creating a new lab. That is why it asks for the lab name and full lab details. For an employee joining an existing lab, that feels jagged and wrong.

**Part of the app involved**
Primary files/components:

* `artifacts/labtrax-desktop/src/components/SignupWizard.tsx`
* `artifacts/labtrax-desktop/src/lib/api.ts`
* `artifacts/api-server/src/routes/auth.ts`
* `artifacts/api-server/src/routes/organizations.ts`
* `lib/db/src/schema/schema.ts`
* `artifacts/labtrax-desktop/src/components/PlanPickerOnboarding.tsx`

**Likely root cause**
The frontend signup wizard collapses two different intents into one `userType === "lab"` path:

1. “I am creating a lab workspace”
2. “I work at a lab and need to join it”

Right now, choosing lab goes straight to `lab_info`, then later still asks for role selection and join group. That creates the confusing sequence you saw.

The backend is actually in better shape than the frontend. It already has:

* `join_requests`
* `lab_memberships`
* pending join request creation during `/auth/register` when `joinOrganizationId` is supplied
* admin approve/reject routes for join requests
* invite routes

So this should mostly be a signup workflow cleanup, not a broad database rebuild.

**Recommended workflow**

1. Account basics
   Username, email, password.

2. Account category
   Ask: “What are you doing in LabTrax?”

   Options:

   * “Join an existing dental lab”
   * “Create a new dental lab”
   * “I am a dental provider”

3. Join existing dental lab
   Show a lab search field. User types the lab name. Results should show:

   * Lab display name
   * Street address
   * City, state, ZIP
   * Phone if available

   User selects the correct lab and clicks “Send join request.”

4. Email verification
   User verifies email with the current verification code flow.

5. Registration completion
   Create the user with:

   * `userType: "lab"`
   * `role: "user"`
   * `createOrganization: false`
   * `joinOrganizationId: selectedLabId`
   * no lab name/details required
   * no requested role selection

6. Post-signup state
   User lands on a plain dashboard or pending-access screen:

   * “Your request to join [Lab Name] is pending admin approval.”
   * No cases yet.
   * No billing prompt.
   * No admin/user role choice.

7. Admin approval
   Lab owner/admin reviews the join request, approves it, and assigns role:

   * `user`
   * `admin`
   * optionally `billing` / `read_only` if those are active roles in the app

**Important constraints**

* Do not let a public signup self-assign admin.
* Do not ask lab joiners for lab name, license number, lab phone, lab email, or billing plan.
* Do not create a new lab organization unless the user explicitly chose “Create a new dental lab.”
* Keep join requests durable and server-backed.
* Expand `/api/labs/lookup` if needed so it returns enough address detail for confirmation.

**Acceptance criteria**

* A lab employee can sign up, search an existing lab, confirm it by address, send a join request, verify email, and reach an empty/pending dashboard.
* The employee is not asked whether they are an admin or user.
* The employee is not asked to choose a billing plan.
* The admin can see the pending join request from the server and approve/reject it.
* Approval creates or updates an active `lab_memberships` row and assigns the role selected by the admin.
* A true lab creator can still create a new lab with required lab details.

**Regression risks to check**

* New lab creation still works.
* Provider signup still works.
* Invite acceptance still works.
* Existing admin approval routes still work.
* Users with pending join requests cannot see lab cases, invoices, or financial screens before approval.

### Debug Analysis

**Probable root cause**
`SignupWizard.tsx` treats `userType: "lab"` as “create a lab,” not “I am a lab-side person.” The `LAB_STEPS` path sends users through `lab_info`, then `role_select`, `join_group`, and `plan_select`. That is exactly why an employee joining your lab gets asked for lab details and role/billing decisions that should belong to the lab admin.

**Supporting evidence**
The wizard’s `selectUserType("lab")` goes directly to `lab_info`. Registration then sends `practiceName: labName`, `createOrganization: !joinTargetOrgId`, and can create a new lab if no join target is selected. Meanwhile the backend already supports pending join requests through `organizationJoinRequests`, and `/auth/register` creates a pending request when `joinOrganizationId` is provided.

**Alternate hypotheses worth checking**
There may also be a missing or weak UI surface for admins to notice pending join requests. The API routes exist, but Replit should confirm the admin dashboard/settings screen actually loads `/organizations/:organizationId/join-requests`.

**Why this approach is best**
It reuses the existing durable server model instead of adding new tables or a parallel workflow. The risky part is not the database; it is the frontend branching and post-signup UX.

### Step-by-Step Fix Plan
