### Replit Build Brief

**Objective**
Fix the LabTrax dashboard so the logged-in `Admin · SDR1` user no longer triggers repeated `403 Forbidden` errors for admin background endpoints and the live messenger WebSocket either connects correctly or is gated off when unavailable.

**User-visible problem**
The dashboard loads, but Chrome DevTools shows repeated failures:

* `GET /api/admin/backup/schedule` returns `403`
* `GET /api/admin/cleanup/orphaned-media/runs?limit=20` returns `403`
* `GET /api/admin/cleanup/orphaned-media/status` returns `403`
* `GET /api/admin/settings/cleanup-schedule` returns `403`
* `wss://lab-trax.replit.app/ws/messenger?...` fails repeatedly

The UI shows the user as `Admin · SDR1`, so the app appears to believe the user has admin access, while the backend rejects admin utility requests.

**Likely root cause**
There is an authorization/capability mismatch between the frontend dashboard and backend admin routes.

Most likely, the frontend is mounting admin/maintenance widgets for any `Admin` user, but the backend routes require a different role or permission, such as `super_admin`, `platform_admin`, `owner`, or a specific maintenance permission. A secondary issue may exist in the WebSocket auth/token handling, but the `403` admin API failures are the clearest confirmed bug.

Inspect the frontend code that runs on `/desktop/`, especially any dashboard mount effects or admin settings widgets that call:

* `/api/admin/backup/schedule`
* `/api/admin/cleanup/orphaned-media/runs`
* `/api/admin/cleanup/orphaned-media/status`
* `/api/admin/settings/cleanup-schedule`

Inspect backend route definitions and middleware for:

* admin route authorization
* backup schedule endpoints
* cleanup/orphaned media endpoints
* cleanup schedule settings endpoint
* current-user/session role serialization
* `/ws/messenger` WebSocket authentication

Likely files may be named something like:

* `server/routes/admin.ts`
* `server/routes/admin/backup.ts`
* `server/routes/admin/cleanup.ts`
* `server/middleware/auth.ts`

**Implementation plan**

1. Identify the permission expected by each failing admin endpoint.
2. Identify the permission/role exposed to the frontend for the current user shown as `Admin · SDR1`.
3. Decide whether SDR lab admins should be allowed to access backup/cleanup schedule data.
4. If yes, update the backend authorization guard to allow the correct scoped admin role.
5. If no, update the frontend so it does not call those endpoints unless the user has the required capability.
6. Prefer a shared capability such as `canManageSystemMaintenance` or `canViewAdminMaintenance` over string-checking roles in many places.
7. Fix the WebSocket separately by verifying that the token format used by the frontend matches what `/ws/messenger` expects.
8. Add graceful handling so forbidden admin utilities do not spam retries or console errors.

**Constraints and guardrails**

* Do not simply ignore all `403` errors globally.
* Do not broaden admin access blindly if backup/cleanup controls are intended to be platform-only.
* Keep tenant/lab-scoped admins separate from system-wide admins if the app has both concepts.
* Avoid repeated polling/retry loops after a known `403`.
* WebSocket reconnect logic should back off and stop retrying on permanent auth failure.

**Acceptance criteria**

**Regression checks**

* Login as platform/system admin, if that role exists, and verify maintenance controls still work.

### Debug Analysis

**Primary root-cause hypothesis**
The dashboard frontend and backend authorization model disagree about what `Admin` means. The UI treats the user as eligible for admin maintenance calls, but the backend rejects those same calls with `403`.

**Supporting evidence**
The screenshot confirms the user is shown as `Admin · SDR1`. The app itself loads and shows dashboard data, so the session is not totally invalid. The failures are concentrated on `/api/admin/...` maintenance-style endpoints, which strongly points to permission mismatch rather than a general network or login failure.

**Alternate hypotheses worth checking**

* The user’s JWT/session token lacks a recently added admin claim after a role model change.
* The frontend is using stale cached user metadata after login.
* The admin endpoints require CSRF/session cookies, but the API client sends only partial auth.
* The WebSocket token is expired, malformed, or generated for HTTP APIs but not accepted by the WS handler.

**Why the recommended fix is best**
The safest fix is to align the app around explicit capabilities. Either the user can access maintenance APIs and the backend should allow it, or they cannot and the frontend should not call them. That avoids both security drift and cosmetic error suppression.

**Confidence level**
Medium-high for the admin API issue. The screenshot is strong evidence of an auth/capability mismatch, but the exact role names and intended permission boundary need code confirmation.
