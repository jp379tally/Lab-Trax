### Replit Build Brief

**Objective**
Fix Unassigned Documents so files uploaded from mobile can be opened on desktop/web, and files opened from desktop/web preview in a separate window instead of downloading.

**User-visible problem**

1. A file uploaded to Unassigned Documents from the mobile app appears in desktop/web, but clicking view shows a red “Could not open file” error.
2. A file uploaded from desktop/web can be opened, but clicking it often triggers a browser/download behavior instead of showing an inline preview.

**Likely root cause**
Mobile and desktop/web are finalizing chunked uploads differently.

The server’s `/api/media/upload-session/:id` completion response returns both:

* `url`: public/authenticated media URL like `/api/cases/attachment-file/<filename>`
* `filename`: actual stored object key / disk filename

The desktop Unassigned Documents uploader correctly sends `storagePath: result.filename` to `/api/lab-inbox/finalize-session`.

The mobile Unassigned Documents uploader currently sends `storagePath: uploadResult.url`. That means some inbox rows may store a URL where the inbox file-serving route expects a storage filename/object key. Later, `/api/lab-inbox/:fileId/file` cannot find the object and desktop shows the red error.

The download behavior is likely in `artifacts/labtrax-desktop/src/components/UnassignedDocumentsCard.tsx`: `handleView()` fetches the file as a blob and calls `window.open(blobUrl)`. Browsers/Electron may download instead of previewing when the blob type is missing, generic, or unsupported, or when opening a raw blob URL without a preview wrapper.

**Exact code areas to inspect/change**

* `artifacts/labtrax/components/UnassignedDocumentsCard.tsx`

  * Mobile Unassigned Documents upload finalization.
* `artifacts/labtrax/lib/query-client.ts`

  * `chunkedUploadCaseMedia()` return shape; it currently returns only `url`.
* `artifacts/api-server/src/routes/lab-inbox.ts`

  * `/finalize-session`
  * `/:fileId/file`
* `artifacts/labtrax-desktop/src/components/UnassignedDocumentsCard.tsx`

  * `handleView()` preview behavior.
* Optional supporting check:

  * `artifacts/api-server/src/lib/case-media-object-storage.ts`
  * It currently writes object metadata with `contentDisposition: attachment`; prefer inline metadata for previewable media if any direct object-storage path is ever used.

**Implementation plan**

1. Update `chunkedUploadCaseMedia()` so successful results include both `url` and `filename` when the server returns them.
2. In mobile `UnassignedDocumentsCard`, call `/api/lab-inbox/finalize-session` with `storagePath: uploadResult.filename`, not `uploadResult.url`.
3. Add a server-side normalization helper in `lab-inbox.ts` that converts legacy full media URLs into their final stored filename. Use it in:

   * `/finalize-session`, before validating object storage.
   * `/:fileId/file`, before resolving disk path or object storage key.
4. This server normalization should also repair already-created bad inbox rows at read time, without requiring an immediate database migration.
5. In desktop `handleView()`, replace raw `window.open(blobUrl)` with a dedicated preview window:

   * Fetch the file with auth.
   * Build a blob with an explicit type from `file.mimeType` or response `Content-Type`.
   * For PDFs, open a new window containing an `<iframe>` or `<object>` pointing at the blob URL.
   * For images, open a new window containing an `<img>`.
   * For unsupported Office files, show a simple preview window explaining that browser preview is not supported and provide an explicit “Download” button instead of auto-downloading.
6. Ensure the API route keeps returning `Content-Disposition: inline`.

**Constraints and guardrails**

* Do not change assignment behavior.
* Do not make Unassigned Documents public; keep auth checks intact.
* Do not bypass `/api/lab-inbox/:fileId/file`.
* Do not store full URLs as `storagePath` for new inbox rows.
* Preserve support for existing bad rows that may already contain full URLs.
* Avoid revoking the blob URL immediately after opening the preview window.

**Acceptance criteria**

* Upload a PDF from mobile to Unassigned Documents, then open it from desktop/web: it previews successfully.
* Upload an image from mobile to Unassigned Documents, then open it from desktop/web: it previews successfully.
* Upload a PDF from desktop/web, then click view: it opens in a separate preview window, not an automatic download.
* Upload an image from desktop/web, then click view: it opens in a separate preview window.
* Unsupported document types do not silently auto-download; they show a preview-window fallback with an explicit download action.
* Assignment from Unassigned Documents still works after viewing.
* Existing mobile-created inbox rows with URL-shaped `storagePath` or `objectStorageKey` can still be opened if the underlying object exists.

**Regression checks**

* Check mobile camera/photo upload to Unassigned Documents.
* Check mobile document picker upload to Unassigned Documents.
* Check desktop drag/drop upload to Unassigned Documents.
* Check desktop file picker upload to Unassigned Documents.
* Check `/api/lab-inbox/:fileId/file` returns `200`, correct `Content-Type`, and `Content-Disposition: inline`.
* Check a missing object still returns a clean 404/error instead of crashing.

### Debug Analysis

**Probable root cause**
The mobile unassigned-document flow is saving the wrong storage identifier. The server expects the generated filename/object key, but mobile sends the upload URL. Desktop/web later asks `/api/lab-inbox/:fileId/file` for the bytes, and that route cannot resolve the file, producing the red open error.

**Supporting evidence**
In the repo, desktop Unassigned Documents uses `storagePath: result.filename` when finalizing. Mobile Unassigned Documents uses `storagePath: uploadResult.url`. The upload-session server completion returns both `url` and `filename`, and the inbox serving route resolves files from `storagePath` / `objectStorageKey`.

**Alternate hypotheses worth checking**
The object-storage metadata currently uses `contentDisposition: attachment`, which could contribute to download behavior if a direct storage URL is ever opened. Also, some uploaded files may have weak MIME types like `application/octet-stream`, which makes browser preview unreliable.

**Why this approach is best**
Fixing only the mobile client would help new uploads, but existing bad inbox rows could still fail. Fixing only the server would protect old rows, but mobile would keep writing bad data. The best fix is both: write the correct key going forward, and normalize legacy URL-shaped values on the server.

**Confidence level**
High for the mobile-to-desktop open failure. Medium-high for the download/preview issue because the desktop code currently opens a raw blob URL and leaves preview behavior to the browser/Electron runtime.

### Step-by-Step Fix Plan

3. In mobile `UnassignedDocumentsCard`, finalize inbox uploads with `storagePath: uploadResult.filename ?? extractedFilenameFromUrl(uploadResult.url)`.

5. Use that helper in `/finalize-session` and `/:fileId/file`.
6. Update desktop `handleView()` to open a real preview window with PDF/image rendering instead of opening the raw blob URL.
